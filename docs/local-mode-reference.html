Local Mode

A mail client whose source of truth is a SQLite file in your browser. The provider is something it reconciles against, not something it waits for. This is how every layer of that works — storage, routing, provider rules, and the three independent cursor systems that make sync resumable.

§1The shape

Two colour codes run through this whole document and through the code itself. local means SQLite — the mirror, instant, works offline. provider means the network — Gmail or Microsoft Graph, slow, fallible, authoritative.

Every read serves local and refreshes from provider behind the response. Every write goes to provider first, then updates local. Hold those two sentences and most of the codebase follows.

Layer mapeach layer calls only downward

The naming trap

mail/graph*.ts is Microsoft Graph, the API. rpc/codecs/microsoft.ts is the Microsoft account, our rules. Same company, different layers. There is no graph.ts under codecs/ — the files are named after the account (google.ts, microsoft.ts), not after the API.

§2Storage

2.1Why a Web Worker

The database is SQLite compiled to WASM, stored in OPFS. It runs in a worker for one hard reason: the SAH-pool VFS needs FileSystemFileHandle.createSyncAccessHandle, which browsers expose only in workers — never on the main thread.

db/client.ts spawns that worker and wires Drizzle's sqlite-proxy driver to it over postMessage. Every query is an async round trip.

Constraint you will hit

sqlite-proxy does not implement db.transaction() — it throws. Multi-statement atomic writes must use db.batch([...]). Reads are unaffected.

2.2Tables

TableHoldsNotable

attachmentsMetadata + cached base64body null until fetched; ≤10 MB kept
labels / thread_labelsJoin table, thread ↔ labelFolder membership is a label row

Folder membership being a label row is why one query can filter by folder and label — and why the SQL in §6.2 has to count distinct matches rather than just filter.

2.3Migrations

drizzle-kit's file migrator does not run in a browser, so db/migrations.ts is an ordered array checked against PRAGMA user_version. After entry N (0-indexed) applies, user_version becomes N+1.

The one ruleappend only
// Entries 0000–0005 have shipped. user_version is 6. Never edit or reorder
// a shipped entry — a browser that already applied it will never re-run it.
MIGRATIONS[6] = [
  `ALTER TABLE threads ADD COLUMN is_read integer NOT NULL DEFAULT 0`,
];

Existing users already hold a populated mirror, so ADD COLUMN gives every stored row the default. Choose a default that is safe when wrong, or invalidate the folder TTLs so the data re-pulls.

§3The tRPC layer

The UI calls trpc.mail.listThreads.useInfiniteQuery(...) exactly as it would against a server. There is no interception step and no fallthrough: tRPC's own unstable_localLink is the only link configured, and it invokes the procedure in-process.

providers/query-provider.tsxthe whole "transport"
const localRouterLink = unstable_localLink({
  router: localRouter,
  createContext: async () => ({}),        // db/driver ctx is built per call by the middleware
}) as unknown as TRPCLink<AppRouter>;

export const trpcClient = createTRPCClient<AppRouter>({ links: [localRouterLink] });

No HTTP, no serialization, no transformer. The cast is the last thread back to the server: the client is still typed against AppRouter while the router it actually runs is localRouter. That goes when the type flips to typeof localRouter.

Every namespace the UI calls is in rpc/router.ts — twelve of them, including stubs for ai, bimi, brain and meet. Nothing falls through to a backend, so a namespace that is missing is a runtime error rather than a silent network call.

initTRPC refuses to run in a browser

initTRPC.create() throws "You're trying to use @trpc/server in a non-server environment" unless you opt out. Running in the browser is the entire point here, so rpc/trpc.ts passes { allowOutsideOfServer: true }. It throws at module evaluation, which is worth knowing: the failure surfaces later and elsewhere as useTRPC() can only be used inside of a <TRPCProvider>, because query-provider.tsx imports the router above the line that creates the context, so the module dies before TRPCProvider is ever assigned.

3.1The three procedure types

rpc/trpc.ts is our own initTRPC.create(). Procedures are stacked middleware, and picking the right one is most of what writing a route involves.

ProcedureAdds to ctxUse when
publicProcedure nothing Pure or localStorage-backed. Stubs.
dbProcedure ctx.db Touches the mirror only. Boots the worker on first use.
driverProcedure ctx.db, ctx.codec, ctx.driver Anything provider-aware — including folder naming.

driverProcedure also does something invisible but essential: it waits for activation. On a page reload React Query fires before the session has been restored, so the driver does not exist yet. Rather than fail, the call parks — see §11.

rpc/trpc.tsdriverProcedure
export const driverProcedure = dbProcedure.use(async ({ next }) => {
  try { await whenActive(); }                    // parks until a driver exists
  catch (err) { throw new TRPCError({ code: 'TIMEOUT', ... }); }

  if (!getTokenProvider()) throw new TRPCError({ code: 'UNAUTHORIZED', ... });
  return next({ ctx: { codec: codec(), driver: getActiveDriver() } });
});

What the router buys over the flat resolver map it replaced: Zod parses the input and applies defaults, the middleware chain supplies context, and errors carry real TRPCError codes instead of whatever the handler happened to throw.

A handful of callers bypass the client and invoke a procedure directly through localCaller (rpc/router.ts) because they want to own their own query key — hooks/use-thread-groups.ts is the one to look at.

Zod strips what it does not declare

An input schema narrower than what callers actually send will silently drop fields. This is why mail.send declares recipients as z.union([z.string(), z.array(...)]) and attachments with both base64 and data keys — the schema must be at least as wide as the function that consumes it.

§4Codecs

Gmail and Graph disagree about nearly everything, and each disagreement cascades. A codec is the translation between one provider's way of organising mail and the mirror's, which is labels all the way down. rpc/codecs/ is where each provider's answers live, written once, in a file named after the account it belongs to.

QuestionGmailGraphCascades into
Folders or labels? Labels — many per thread Folders — exactly one per message Move exclusivity
Is there an Archive? No — "filed nowhere else" Yes, a real folder Fetch by search vs by id
Complete label set? Yes No — one message's folder Replace vs merge
Can absence mean removal? No — replacing covers it Yes — the only signal there is Pruning
Folder hierarchy? Naming convention a/b A real tree Tree reconstruction
Delta scope? Whole mailbox, one cursor Per folder, N cursors Poll targets, batching

4.1One file per provider

google.ts and microsoft.ts export the same six members with the same signatures. That is deliberate — you can diff them side by side.

MemberDirectionDecides
id — 'google' | 'microsoft', also the providerId written to rows
folderKey(name) UI → mirror 'bin' → TRASH / deleteditems
mirrorLabels(ids, listedUnder?) provider → mirror What labels a fetched thread is filed under
mirrorEdit(add, remove) UI → mirror Translation, exclusivity, and the folderMove flag
toFolderRows(...) provider → mirror Label list / folder tree → sidebar rows
pollTargets(folders) mirror → provider Which folders to delta-poll, under what key
replaceLabels flag Replace vs merge on a mirror write

Both files are pure — types only, no client, no db. That is not decoration: it is what lets every provider decision be read in one sitting, and what keeps the fetching and the SQLite writes in one shared place (rpc/local-utils.ts) instead of duplicated per provider. These bugs are silent — a wrong parent nests a folder wrongly, a wrong exclusivity leaves a thread in two places. Nothing throws.

4.2The one branch

rpc/codecs/index.tsthe only if provider === in the local layer
export function codec(): Codec {
  const token = getTokenProvider();
  if (!token) throw new Error('local mail: not signed in');
  return token.provider === 'microsoft' ? microsoftCodec : googleCodec;
}

A lookup, not a factory. The codecs are frozen objects of pure functions, so there is nothing to build, nothing to memoize, and nothing to invalidate on reconnect — which is the whole reason the earlier createGoogleSync(driver, client) wiring went away.

4.3The cascade, side by side

The fetching lives once in syncThreadPage; the codec supplies the two answers that differ.

rpc/local-utils.tssyncThreadPage — one body, two answers
const c = codec();
// Archive is not a Gmail label but "filed nowhere else", so it is fetched as a search.
const selector = c.id === 'google' && key === 'archive'
  ? { q: 'in:archive' } : { labelId: key };

const page = await withRetry(() => getActiveDriver().listThreads({ ...selector, maxResults: 25 }));
await mirrorThreads(db, page.threads, key);   // applies c.mirrorLabels + c.replaceLabels
await hydrateStubs(db, page.threads);

// google    replaceLabels: true  — REPLACE, so no prune: replacing already removed what left
// microsoft  replaceLabels: false — MERGE, and merging never removes...
if (c.id === 'microsoft' && !pageToken) {      // ...therefore PRUNE
  const since = /* oldest latestReceivedOn in this page */;
  await pruneFolderMembership(db, key, ids, since);

await setPageCursor(db, c.id, key, page.nextPageToken);

Two guards on the prune, both load-bearing. Bounded by date — older threads were never in the window, so their absence proves nothing. First page only — a paged read is not the current top of the folder and would prune threads that are simply on an earlier page.

§5Client & driver

Inside mail/ the split is one line: the client knows the wire, the driver knows our row types. Neither touches SQLite.

A Gmail API change touches gmail-client.ts. A rule change — where archived mail files, what counts as a move — touches codecs/google.ts. The MailDriver interface is what lets codecs/ stay ignorant of both.

5.1Where sync reaches past the driver

Threads and messages go through the driver, already normalized for both providers. The folder tree is the one read that does not: syncFolderTree calls getActiveClient() directly, because a folder tree only ever becomes mirror rows, so each codec maps its own provider's raw listing straight to them. Normalizing it first would strip exactly the parentage the mapper needs.

Two paths outthe driver is not always the answer
syncThreadPage()  ──► driver.listThreads()  ──► client.listThreadIds()  ──► HTTP
                        (mapping)                (transport)

syncFolderTree()  ──────────────────────────► client.listLabels()      ──► HTTP
                                                 (raw, keeps parentage)
                                             ──► codec.toFolderRows()

This is also the only place the codec lookup is done by module rather than through codec() — syncFolderTree imports both codecs by name, because the two toFolderRows take different argument types (Gmail's flat labels vs Graph's tree roots) and a shared signature would be a lie.

§6Reading a list

mail.listThreads is a dispatcher over four modes. The procedure body itself is a table of contents; each mode is a named function that reads top to bottom.

6.1Why search blocks and a folder does not

The deliberate divergence
// searchPage — awaits
if (claimRevalidate(key)) await dedupe(key, () => syncSearch(a.db, q));
return toPage(a.db, await read());

// folderPage — does not
revalidateTargets(a.db, targets);      // no await
return toPage(a.db, cached);

Stale hits for a term the user just typed read as broken. A slightly stale folder reads as instant. Same machinery, opposite call.

6.2The SQL, two mechanisms

Labels are AND, not ORdb/queries.ts
const required = [...new Set([folderLabel, ...(labelIds ?? [])])];
.where(inArray(threadLabels.labelId, required))
.groupBy(threads.id)
.having(sql`count(distinct ${threadLabels.labelId}) = ${required.length}`)

thread_labels is a join table — one row per (thread, label). Matching INBOX and IMPORTANT means matching two different rows for the same thread. So: pull rows matching either, group by thread, keep only threads that matched all of them. The new Set matters — a duplicate would inflate required.length and match nothing.

Keyset pagination, not OFFSET
.orderBy(desc(threads.latestReceivedOn), desc(threads.id))
.limit(maxResults + 1)                       // 26 to answer "is there more?"

const nextPageToken = `${last.latestReceivedOn}|${last.id}`;

// next page asks: older than that timestamp, OR same timestamp and lower id
or(lt(latestReceivedOn, ts), and(eq(latestReceivedOn, ts), lt(id, id)))

OFFSET 25 would break: new mail arrives between pages, shifts everything down, and you see row 25 twice. Keyset asks "older than this specific row", which is stable no matter what lands above it. The id is the tiebreaker — two mails in the same second would otherwise repeat or skip.

6.3Batched rendering

Rendering a page used to be a nested N+1: 25 rows, each calling mail.get, each running 3 queries plus one per message — roughly 100 worker round trips. getThreadBundles replaced it with four flat queries regardless of N:

db/queries.tsgetThreadBundles
threads      where inArray(threads.id, threadIds)
messages     where inArray(messages.threadId, threadIds)  order by receivedOn
labels       join threadLabels where inArray(threadLabels.threadId, threadIds)
attachments  where inArray(attachments.messageId, <ids from the message rows>)

listThreads returns those rendered rows alongside the ids, and use-threads.ts seeds them into mail.get's cache. The seeding is fill-only — an existing entry may be a thread the user opened, holding real bodies the row copy lacks. Clobbering it would blank the reader on every list refetch.

§7Cursors

Three independent cursor systems, easy to confuse, doing genuinely different jobs. This is the section to know cold.

CursorAnswersFormatStored inSurvives reload
Keyset How far has the UI scrolled the mirror? ts|id React Query pages (memory) no
Page token How far has sync read the provider? opaque, provider's own sync_state · page:<id> see §8.3
Delta What has changed since last poll? historyId / deltaLink folders.deltaCursor yes

7.1Where the first two meet

Only one code path touches both, and it is the one that makes infinite scroll deepen the mirror:

folderPagekeyset runs out → page token advances
if (a.cursor) {                              // a KEYSET cursor from the UI
  const page = await read();
  if (page.threads.length > 0 || isOffline()) return toPage(a.db, page);

  // Mirror is dry. Pull the next PROVIDER page using the stored page token...
  await dedupe(`page:${a.folderId}`, () => syncNextPage(a.db, a.folderId));
  return toPage(a.db, await read());   // ...then re-read with the SAME keyset cursor
}

The keyset cursor never changes during that exchange. What changed is how much the mirror holds. That is the entire mechanic: scroll deepens storage, and the depth is permanent.

7.2Setting a page cursor

rpc/sync-state.ts
const pageScope = (folderId: string) => `page:${folderId}`;

export function setPageCursor(db, providerId, folderId, cursor: string | null) {
  return setSyncState(db, pageScope(folderId), providerId, new Date().toISOString(), cursor);
}

export async function getPageCursor(db, folderId): Promise<string | null> {
  return (await getSyncState(db, pageScope(folderId)))?.cursor ?? null;
}

A search reuses the same mechanism under a different key — setPageCursor(db, id, \`search:${q}\`, token) produces scope page:search:<q>. Each query term paginates independently.

When the provider returns nextPageToken: null, that null is stored. A subsequent syncNextPage reads null and returns false — the folder is fully mirrored, stop asking.

7.3The delta cursor lives elsewhere

Delta cursors are a column on folders, not a sync_state row:

db/queries.ts
export async function setFolderDeltaCursor(db, folderId, cursor: string | null) {
  await db.update(folders).set({ deltaCursor: cursor }).where(eq(folders.id, folderId));
}
Gmail's cursor has a surprising home

Gmail's history is mailbox-wide — one cursor covers every label. But deltaCursor is a per-folder column. So Gmail's single historyId is stored on the inbox folder row, because google/folders.ts's pollTargets returns only that row, tagged folderKey: null to mean "this cursor speaks for the whole account".

pollTargetssame signature, different arity
// google/folders.ts — one target, null key
folders.filter((f) => f.role === 'inbox').map((f) => ({ folder: f, folderKey: null }))

// microsoft/folders.ts — one target per tracked role, each with its own key
folders.filter((f) => f.role && POLLED_ROLES.has(f.role))
       .map((f) => ({ folder: f, folderKey: FOLDER_KEYS[f.role!] ?? f.role! }))

POLLED_ROLES is inbox, sent, archive, trash, spam. Drafts are excluded — they are the outbox's business.

rpc/sync-state.ts is a thin namespaced layer over one table. Four columns: scope (primary key), providerId, cursor, syncedAt.

Everything is keyed by a prefixed scope string, which is what makes selective invalidation possible.

8.1Freshness

The TTL gateSYNC_TTL_MS = 2 minutes
async function isStale(db, scope, now) {
  const row = await getSyncState(db, scope);
  if (!row?.syncedAt) return true;              // never synced === stale
  return now - Date.parse(row.syncedAt) >= SYNC_TTL_MS;
}

markFolderSynced and markThreadSynced stamp syncedAt. A subtlety in setSyncState: omitting cursor leaves the stored one intact; passing null clears it. That distinction is what lets markFolderSynced refresh a TTL without destroying a cursor.

8.2Invalidation is prefix-scoped

CallDeletesUsed after
invalidateThread(id)thread:<id>A targeted change
invalidateAllFolders()LIKE 'folder:%'Any write — thread freshness survives
resetSyncState()everythingmail.forceSync

invalidateAllFolders being prefix-scoped is the point: after a label write, every folder listing is suspect but the threads themselves are not, so their TTLs are left alone.

8.3Resume — and where it currently breaks

The design intent is stated at the top of sync-state.ts: "Persisted, not in-memory, so a reload resumes instead of re-pulling every folder." The table does live in OPFS and does survive a reload.

But activation wipes it. On every page load:

rpc/activate.tscalled from LocalMode's restore effect
export async function activateLocal(p: TokenProvider) {
  localStorage.setItem('local.email', email);
  installLocalSessionPatch();
  setActiveProvider(p);
  try {
    await resetSyncState(await getLocalDB());   // ← DELETE FROM sync_state WHERE 1=1
  } catch { /* mirror may not exist yet on a first login */ }
  await getSession();
}
Finding · verified in source

resetSyncState is clearSyncState(db) with no scope argument, which issues DELETE FROM sync_state WHERE 1 = 1. Because LocalMode calls activateLocal after every successful restoreSession(), this runs on every reload.

Consequences. Every folder re-syncs on load (TTLs gone). Scroll depth restarts from provider page 1 (page: tokens gone). Most seriously, snoozed threads never wake — the SNOOZED label persists on the thread but the snooze:<id> row holding wakeAt is deleted, so dueSnoozes finds nothing and the thread stays out of the inbox permanently.

What still survives: all mirrored mail, the folder tree, and folders.deltaCursor — because the delta cursor is a column on folders, not a sync_state row. Delta polling does resume correctly.

The narrow fix is to scope the reset — clear folder: and page: on activation if a cold start is wanted, and leave snooze: alone. Or drop the call entirely and let the TTLs do their job, which is what they exist for.

§9Delta poll

Every 120 seconds, and once on mount, LocalMode calls pollChanges() — skipped when the tab is hidden or the driver is inactive.

rpc/local-utils.tspollChanges, annotated
// 0. Tabs share one mirror: a second poller is duplicate API calls and two writers
//    racing the same delta cursors. pollChanges() = withTabLock('zero-poll', ...).
const c = codec();
const inboxFolder = c.folderKey('inbox');

// 1. Snoozes are local, so they wake with or without a network.
const woke = await wakeSnoozed(db, inboxFolder);
if (woke) emitMirrorChanged();
if (isOffline()) return;

// 2. Ask the codec which folders are worth polling.
//    google → [inbox] with folderKey: null   microsoft → five folders, own keys
const polled = c.pollTargets(await getFolders(db, c.id));

// 3. Graph's delta is per-folder: N folders = N reads, unless the driver can batch.
//    Gmail needs none of this — one history read covers every label.
if (driver.listChangesMany && polled.length > 1) {
  byFolder = await driver.listChangesMany(
    polled.map(({ folder }) => ({ folderId: folder.id, cursor: folder.deltaCursor ?? null })),
  );
} else for (const { folder, folderKey } of polled) {
  byFolder[folder.id] = await driver.listChanges!(
    folderKey === null ? null : folder.id,   // null = whole mailbox (Gmail)
    folder.deltaCursor ?? null,
  );
}

9.1Applying a delta page

per folder
if (changes.resyncRequired) {              // cursor aged out at the provider
  await setFolderDeltaCursor(db, folder.id, null);
  await syncFolder(db, folderKey ?? inboxFolder);   // full re-read instead
  markRevalidated(full);
  continue;
}

await mirrorThreads(db, changes.threads, folderKey ?? undefined);
await deleteMessagesByIds(db, changes.removedMessageIds);
await setFolderDeltaCursor(db, folder.id, changes.cursor);        // ← advance
await markFolderSynced(db, c.id, folderKey ?? inboxFolder, changes.cursor);
markRevalidated(folderKey ?? inboxFolder);

resyncRequired is the provider saying "that cursor is too old, I can no longer tell you what changed." Graph signals it with a specific error code; the driver translates it into this flag. The recovery is to drop the cursor and do a full folder read — the next poll starts a fresh delta chain.

markRevalidated is subtle but load-bearing: it stamps the target as just-refreshed without asking, so the emitMirrorChanged at the end does not re-enter listThreads and fire a redundant full sync.

9.2How a background sync reaches the screen

rpc/dedupe.ts → local-mode.tsxthe notification loop
sync writes SQLite
   │
   ▼
emitMirrorChanged()          // batched, 200 ms — 25 threads landing = 1 notification
   │
   ├──► broadcastMirrorChanged() ──► other tabs (SharedWorker port)
   │                                    └─► their listeners fire immediately, no re-batch
   ▼
LocalMode's onMirrorChanged listener
   │
   ▼
queryClient.invalidateQueries(mail.listThreads, mail.get,
                              mail.getMessageAttachments, drafts.*)
   │
   ▼
React Query re-runs the resolver ──► reads SQLite ──► UI updates

The 200 ms window is a trailing throttle, not a debounce: the first call arms the timer and later calls are dropped rather than resetting it, so a steady stream of emits still lands on time. The receiving tab does not re-batch — the writing tab already waited out its window before broadcasting.

Three guards keep this loop from feeding itself, all in rpc/dedupe.ts except the last. dedupe(key, fn) collapses concurrent syncs of the same target onto one promise — clicking through folders must not fan out N fetches. withTabLock(name, fn) does the same one scope up, across tabs. claimRevalidate(key) (in local-utils.ts) is a 5-second-per-target gate, which is what stops the invalidate → resolver → sync → emit cycle from running forever.

§10Writing

10.1Label edits — provider first

modifyThreadrpc/local-utils.ts
const db = await getLocalDB();
await getActiveDriver().modifyLabels(threadId, add, remove);   // 1. provider is truth

const edit = codec().mirrorEdit(add, remove);                  // 2. translate…
await applyThreadLabels(db, threadId, edit.add, edit.remove);  //    …then mirror follows

await afterThreadWrite(db, threadId, edit.folderMove);          // 3. re-read behind

Order matters. If the provider rejects the change, nothing else should happen — the mirror only ever records what the provider has already accepted, so it cannot drift into claiming a state the server refused. Optimistic UI is React Query's job, not the mirror's. And edit.folderMove — from mirrorEdit — decides whether step 3 does a full thread re-read: Graph re-ids every message when a thread changes folder, so the ids in the mirror go stale.

10.2Sends and drafts — outbox first

Everything the user composes lands in the outbox table synchronously and the procedure returns. That is what makes composing, saving and sending work with no network. rpc/outbox.ts drains it in the background every 15 seconds and on the online event.

The send lifecycle
queueSend()          row: kind=send, status=queued, sendAfter=now+15s (undo window)
   │                 mirrorPendingSend() → placeholder thread appears in Sent
   ▼
drain() picks it up once sendAfter has passed
   │
   ├─ success ──► delete draft copy, delete outbox row, invalidateAllFolders
   │              reconcileSent() polls Sent at 0/1.5/4/10/20 s
   │              // Graph answers 202 Accepted — the message lands *later*
   │
   └─ failure ──► attempts++, backoff [0, 30s, 2min]
                  after 3 attempts → parked as a draft with the error, toast shown
                  // never retried forever: a timeout after the provider accepted would send twice

The placeholder holds the body and the attachment bytes, and is not dropped until the real message is mirrored in full. Dropping it early is what previously left sent mail with its attachments missing — a folder listing yields only stubs, and a stub has no attachment rows.

§11Lifecycle

On reload, two things race: React Query fires immediately, while restoreSession() takes a few hundred milliseconds to refresh the token.

The reload sequence
t=0ms     page loads. driver = null
t=5ms     React mounts, useThreads fires mail.listThreads
t=5ms     unstable_localLink routes it to localRouter — there is nowhere else to go
t=5ms     driverProcedure → whenActive() → no driver → parks
          // creates a promise, stores its resolve in activeWaiters, suspends
t=400ms   restoreSession() resolves → activateLocal → setActiveProvider(p)
          → settleWaiters(null) → every stored resolve() fires
t=401ms   parked calls resume, read SQLite, mailbox renders

"Parked" means suspended, not polling: the request is alive but frozen on an await until one event releases all of them at once.

OutcomeWaiters get
Driver arrivesresolve() — carry on
Sign-out / failed restorereject('local mail: activation cancelled')
15 s with neitherreject('activation timed out'), self-removes from the list

Every exit path settles the queue. An earlier version skipped the flush when the driver was null, so a failed restore left promises that never settled and array entries that never cleared.

11.1Sign-out

localSignOut() revokes at the provider (best-effort), clears the driver, drops the whole mirror, and clears the IndexedDB React Query cache — that last one because the persisted cache is keyed by a null connectionId, so without it one account's mail would bleed into the next.

connectionId is a leftover from server mode, where a user could hold several linked mailboxes and the active one had a row id to scope the cache by. Local mode has one provider at a time, so root.tsx passes null and nothing ever computes it: every query key gets the same constant prefix and the persister always lands in the -default bucket. That is exactly why the idbClear() above has to be explicit — with a real id, switching accounts would change buckets by itself.

12.2Add a field — bottom up

Say isRead on threads. Six steps, in this order:

  1. Migration — append entry 0006, never edit a shipped one
  2. Schema — must match the migration exactly
  3. Driver — populate it on both sides. Gmail: !labelIds.includes('UNREAD'). Graph: msg.isRead, and add the field to MESSAGE_SELECT or Graph will not return it
  4. Writer — check hydrateThreads' upsert set clause carries the new column, or it inserts once and never updates
  5. Reader — whichever query the UI uses
  6. Route — pass it through

Step 3 has real logic and mapping bugs are silent — exercise both providers by hand before calling it done.

12.3Add an endpoint — top down

Opposite direction. Write the route against SQLite first, assuming the driver has what you need. Then the query, then the MailDriver method (in mail/types.ts, implemented in both drivers), then the client call.

12.4When the providers disagree

The rule that keeps this from rotting:

  1. Never write if (provider === 'microsoft') outside codecs/index.ts
  2. Add the member to both codecs with the same signature — always, even if one side is a no-op. A member on one codec only is a branch in disguise
  3. Keep it pure. If the decision needs a client or a db handle, the decision belongs in the codec and the doing in rpc/local-utils.ts
  4. Widen the Codec type by adding the member, not by casting at the call site

12.5Verification

§13Exam drill

Why does syncThreadPage prune for Graph but not Gmail?

Because Gmail returns a thread's complete label set, so the mirror replaces — which already removes anything that left. Graph reports only one message's folder, so the mirror must merge; merging never removes, so absence from a folder listing becomes the only removal signal available. The prune follows from the merge, which follows from what the API reports.

Name the three cursors and where each is stored.

Keyset ts|id — the UI's scroll position in the mirror, held in React Query's infinite pages, not persisted. Page token — how far sync has read the provider, sync_state scope page:<folderId>. Delta cursor — what changed since last poll, folders.deltaCursor column.

Where does Gmail's mailbox-wide historyId get stored, and why is that odd?

On the inbox folder row's deltaCursor column. It is odd because the cursor is not per-folder at all — but deltaCursor is a per-folder column, and codecs/google.ts's pollTargets returns only the inbox row, tagged folderKey: null to signal "this speaks for the whole mailbox".

You scroll past the end of the mirror. Trace what happens.

folderPage sees a keyset cursor, reads SQLite, gets zero rows. It calls syncNextPage, which reads the stored provider page token from sync_state scope page:<folderId>, pulls that provider page into the mirror, and stores the new token. Then it re-reads SQLite with the same keyset cursor, which now finds rows. If the stored token was null, syncNextPage returns false — the folder is fully mirrored.

Why limit(maxResults + 1)?

To answer "is there another page?" without a second COUNT(*) query. Fetch 26, and if 26 came back, drop the extra and emit a cursor built from row 25.

What does markRevalidated prevent?

An infinite loop. A sync ends with emitMirrorChanged, which invalidates listThreads, which re-runs the resolver, which would see a stale TTL and sync again. markRevalidated stamps the target as just-refreshed without asking, so the re-entry finds it fresh.

Why does setSyncState distinguish an omitted cursor from a null one?

So that markFolderSynced can refresh a TTL without destroying a stored cursor. Omitted leaves it intact; null explicitly clears it — which is what the resyncRequired path wants.

What survives a page reload, and what does not?

Survives: everything in OPFS — threads, messages, attachments, labels, folders including deltaCursor, and the outbox. Does not: the entire sync_state table, because activateLocal calls resetSyncState on every activation. That takes TTLs, page tokens and snooze wake times with it. See §8.3 — the snooze loss is a genuine bug.

Which procedure type would you use for a route that only reads the mirror?

dbProcedure — unless it needs folder naming. folderKey() lives on ctx.codec, which only driverProcedure supplies, so anything translating a UI folder name needs the driver tier even if it never touches the network.

Why does the snoozed view never sync?

SNOOZED is a label that exists only in our SQLite. The provider has never heard of it and still reports those threads as being in the inbox, so a sync would immediately undo the snooze.

What is folderMove for?

Graph re-ids every message in a thread when the thread changes folder, so the message ids in the mirror go stale. folderMove is the signal to re-read the whole thread behind the response rather than trust the label edit.

Why must the Graph prune be bounded by date and restricted to the first page?

Date: threads older than the page's window were never candidates for return, so their absence proves nothing. First page: a paged read is not the current top of the folder, so it would prune threads that are simply on an earlier page.

Why can't you use db.transaction()?

The sqlite-proxy driver does not implement it — it throws. Atomic multi-statement writes go through db.batch([...]), which the client wires to the worker's batch path.

What breaks if a Zod input schema is narrower than the caller sends?

Nothing throws — Zod strips undeclared keys silently. The handler then sees a field as undefined that the caller definitely sent. This is why mail.send's attachment schema accepts both base64 and data, and recipients accept both a comma-joined string and an array.
